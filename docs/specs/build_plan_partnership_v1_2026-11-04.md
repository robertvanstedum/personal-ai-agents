# Partnership workflow modular build plan

**Version 1.0 · 4 November 2026 · Application edition**

Claude Code is the intended implementation lead. Codex owns specification/acceptance and is the implementation fallback if capacity is exhausted. Independent review follows the code author, not the brand: if Codex builds a batch, another qualified non-author must review it before release. A credit interruption must not force bypassing review.

## Start and scope

Under an explicit owner kickoff, begin with B0 read-only feasibility and baseline work, then proceed into the authorized isolated synthetic implementation if no blocking contradiction exists. The private kickoff records the actual implementer and authorized scope; this reusable document is not itself an execution grant. New authority, data migration, public implementation publication, live deployment and paid route activation remain separately gated.

Authority cleanup is a predecessor to replacing restrictive transports or exposing real tools. Correct existing defects in bounded independently reviewed patches; do not wait for a new UI to make unsafe behavior acceptable. Every package returns observable evidence, not merely a new API.

## Defaults that let synthetic work start

Use an independent task-service container design; implementation tests run isolated. Default timezone/return preferences are configurable; test both verified-meeting and 08:00-next-day fallback without asserting a real meeting. Preserve all history initially; archive filters are views and no automatic deletion is introduced. Synthetic job-description/design corpora unblock J1; real source selection gates real-source acceptance only. Seven Practice Book templates are proposals/fixtures; no private incident or live card adoption is fabricated.

These choices do not settle future production resources, retention deletion, private mounts, real grants or spend. Record those decisions separately without blocking unrelated synthetic packages.

## Ownership and handoff contract

Each package MUST have one current editor, one pinned baseline, a declared path/API scope and one non-author acceptance reviewer. Logical module lanes are not permission for simultaneous editing in the shared checkout. A second implementer can take a released package/isolated approved worktree after an explicit writer handoff; shared interfaces change through versioned contracts.

At each reviewable boundary, and before starting a long run, maintain a private checkpoint containing: package ID, implementer/reviewer, worktree/branch/base/HEAD, dirty-file manifest/diff hash, completed requirements, tests and exact commands/results, failures/unknowns, running jobs/locks, approved authority and remaining spend if applicable, next safe command and rollback. Never put credentials in checkpoints.

If Claude Code runs out of credits, Codex reads the latest checkpoint and actual diff, confirms the former writer is stopped and no jobs/locks remain active, claims the writer slot and continues the same package. Preserve authored changes and unresolved findings. Do not rebase/reset another agent's work or re-run uncertain external effects. If stopped mid-command, reconcile the command/process first. Status must distinguish prepared, built, tested, independently reviewed, committed and deployed.

Commit/release boundaries remain those authorized by the owner and repository rules. A local dirty checkpoint is valid; do not fabricate a commit to make handoff look tidy. No main merge or production rollout follows merely from reaching the last package.

## Build as first customer

Before qualified tools exist, the private package/checkpoint register is the temporary build coordination record. After the synthetic receipt/replay/scope acceptance passes and private local use is authorized, record build assignments through the task service; keep code/evidence in their own homes and link them. Distinguish recording an assignment from enabling agent execution. If the new service fails, preserve its journal and use the known checkpoint recovery path without creating conflicting authoritative lists. No build continuity may depend solely on the unverified component being built.

## Review gates

Claude Code closes feasibility against the spec hash and actual code. Codex checks each non-trivial batch's actual diff and acceptance evidence. If authorship changes, name another independent reviewer. Any schema/authority change outside the spec returns for design disposition; routine implementation choices do not require renewed approval. Budget/unknown-outcome stops remain real stops. Finish with a release readiness report stating demonstrated capabilities, omissions and separate decisions required for live use.
