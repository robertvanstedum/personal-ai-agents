My opinion: your instinct is right, and the convention you're reacting against is right for a different kind of repository.
README.md in subfolders is standard in code repositories, and it works there because the folder is the unit — a package, a service — and people navigate by browsing the tree in a web UI that auto-renders the README when you click into the folder. That's the whole value of the fixed name.
Your repository isn't that. It's navigated by agents reading file listings, by search, and by you with fifteen editor tabs open. In every one of those views, README.md carries zero information. The convention is designed for a navigation mode you don't use.
So README_something.md — I'd support it over my --index suggestion, and for a better reason than taste. It's consistent with your existing house convention: ROADMAP_, ARCHITECTURE_, OPERATIONS_ are all uppercase-prefixed. And it gives you a clean two-part rule:
- Records end in --<ulid>. They're content.
- Orientation files start with README_. They're navigation, and for series indexes, they're generated.
Those never look alike in a listing. You can tell at a glance which files are the repository and which are signposts to it. --index would have buried the distinction; the uppercase prefix makes it visible.
Two details to keep:
The nine placeholders still go. README_archive.md that says "nothing here yet" is the same noise with a better name.
Series indexes become README_terminal-pleistocene-briefing.md, generated by the tool you just authorized. The initiative narratives merge into their initiative records — an initiative is content, not a signpost, so it gets a ULID, not a README prefix.
The one thing you lose is GitHub auto-rendering in subfolder views. In a private repository read mostly by agents, that's nothing.
